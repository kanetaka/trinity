# コードレビュースキル

レビュー時は `.claude/rules/project.md` のコード規約・命名規則と、`architecture` スキルのモジュール依存ルールも合わせて確認すること。

## 目的
- 変更コードについて,仕様との整合性を確認する
- バグや設計上の不整合を早期に発見する
- 修正方針がプロジェクトのアーキテクチャと整合しているか判断する
- 実装の保守性,可読性,性能,セキュリティの観点でレビューする

## 基本方針
- 変更の意図を最初に確認し,その意図が要件や問題と一致しているか評価する
- 既存のモジュール責務を尊重し,責務の混在や境界の曖昧さを指摘する
- 測定不能な推測ではなく,コードとデータフローに基づいてレビューする
- 「動くか」だけでなく,「どこに責務があるか」「破壊的変更がないか」「再利用可能か」を確認する
- 公開APIやファイルフォーマット（入出力）を変更する場合は互換性を必ず確認する

## レビュー観点

### 1. 正しさ
- 実装が要件を満たしているか
- エッジケースが考慮されているか
- エラー時の挙動が妥当か
- 例外や失敗時に早期に検出できているか
- Vulkanリソースの生成・破棄、同期（バリア・フェンス・セマフォ）が正しいか

### 2. アーキテクチャ整合性
- Object/Componentの責務分離が守られているか
- 振る舞いがIComponentを実装したコンポーネントとして実装されているか
- 具象クラス同士の実装継承をしていないか
- モジュール依存関係（core → geometry/graphics → scene → renderer → app）が設計方針と整合しているか
- 命名が既存の用語やルールと一致しているか

### 3. 保守性
- 重複コードがないか
- 関数や構造体の粒度が適切か
- コメントや命名が理解しやすいか
- 将来の変更に耐えられるか

### 4. パフォーマンス
- 不要な再計算やメモリ割り当てがないか
- バッチ処理やGPU転送が適切か
- ループ内（特に毎フレーム処理）で重い処理を行っていないか

### 5. セキュリティと信頼性
- 文字列やファイルパスの取り扱いが安全か
- 外部入力（モデル・テクスチャ等のファイル）を信頼せず検証しているか
- 共有状態やグローバル変数を使用していないか
- 競合条件や不正な状態遷移がないか

## レビュー出力の作法
- 問題点は優先度を持って整理する
- 「修正案」だけではなく,「原因」と「影響範囲」を述べる
- 指摘は具体的なファイル名と箇所を含める
- 良い点も併せて示し,改善コメントを建設的に残す
- 重大度が高い指摘は,必ず修正が必要かどうかを明示する

## コメント例
- 「このコンポーネントは描画処理まで抱えているので,renderer側へ責務を移すべきです」
- 「graphicsからsceneのヘッダをincludeしており,モジュール依存方向に反しています」
- 「このループで毎フレームメモリ確保が発生しているので,事前確保か再利用に変えると良いです」
- 「このバッファは破棄前にGPUの使用完了を待っていないため,解放後アクセスの恐れがあります」

## ルール
- 直感や主観ではなく,読み取れるコードと設計判断を根拠にする
- 変更が大きすぎるなら,分割可能な範囲を提案する
- 既存のプロジェクト方針に反する変更を見つけたら,その理由と代替案を示す
- 修正依頼は,一度に複数の独立した懸念をまとめず,優先度順に伝える

## 期待する結果
- 変更の品質を高め,レビュー負荷を下げる
- バグの早期発見とデザインの一貫性維持を支援する
- 「なぜ危険か」「何を直すべきか」を説明できるレビューを行う
