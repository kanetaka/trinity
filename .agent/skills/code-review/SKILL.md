# コードレビュースキル

## 目的
- 変更コードについて,仕様との整合性を確認する
- バグや設計上の不整合を早期に発見する
- 修正方針がプロジェクトのアーキテクチャと整合しているか判断する
- 実装の保守性,可読性,性能,セキュリティの観点でレビューする

## 基本方針
- 変更の意図を最初に確認し,その意図が要件や問題と一致しているか評価する
- 既存のモジュール責務を尊重し,責務の混在や境界の曖昧さを指摘する
- 測定不能な推測ではなく,コードとデータフローに基づいてレビューする
- 「動くか」だけでなく,「どこに責務があるか」「破壊的変更がないか」「再利用可能か」を確認する
- 仕様変更がある場合は,API/JSON-RPC/シリアライズ境界の互換性を必ず確認する

## レビュー観点

### 1. 正しさ
- 実装が要件を満たしているか
- エッジケースが考慮されているか
- エラー時の挙動が妥当か
- 例外や失敗時に早期に検出できているか

### 2. アーキテクチャ整合性
- ECSの責務分離が守られているか
- Componentにロジックが入りすぎていないか
- SystemとViewの責務が混ざっていないか
- モジュール依存関係が設計方針と整合しているか
- 命名が既存の用語やルールと一致しているか

### 3. 保守性
- 重複コードがないか
- 関数や構造体の粒度が適切か
- コメントや命名が理解しやすいか
- 将来の変更に耐えられるか

### 4. パフォーマンス
- 不要な再計算やメモリ割り当てがないか
- バッチ処理やGPU転送が適切か
- ループ内で重い処理を行っていないか

### 5. セキュリティと信頼性
- 文字列やファイルパスの取り扱いが安全か
- 外部入力を信頼せず検証しているか
- 共有状態やグローバル変数の使用が過剰でないか
- 競合条件や不正な状態遷移がないか

## レビュー出力の作法
- 問題点は優先度を持って整理する
- 「修正案」だけではなく,「原因」と「影響範囲」を述べる
- 指摘は具体的なファイル名と箇所を含める
- 良い点も併せて示し,改善コメントを建設的に残す
- 重大度が高い指摘は,必ず修正が必要かどうかを明示する

## コメント例
- 「ここはComponentに状態更新ロジックが混ざっているので,System側へ移すべきです」
- 「この変更は既存のJSON-RPC契約と互換性がないため,後方互換の考慮が必要です」
- 「このループで毎フレームメモリ確保が発生しているので,事前確保か再利用に変えると良いです」
- 「この分岐は表示制御と描画処理が混同しているため,render_state側でのガードに整理した方が責務が明確です」

## ルール
- 直感や主観ではなく,読み取れるコードと設計判断を根拠にする
- 変更が大きすぎるなら,分割可能な範囲を提案する
- 既存のプロジェクト方針に反する変更を見つけたら,その理由と代替案を示す
- 修正依頼は,一度に複数の独立した懸念をまとめず,優先度順に伝える

## 期待する結果
- 変更の品質を高め,レビュー負荷を下げる
- バグの早期発見とデザインの一貫性維持を支援する
- 図式的に「なぜ危険か」「何を直すべきか」を説明できるレビューを行う
